# 催告函与被迫解除通知书

本参考供模型把已完成的分析和用户目标转成两类统一 `document.render` 文书。模型拥有正文、事实解释、风险沟通和候选范围；工具只接收一次性完整正文和显式绑定，负责确定性字段校验、档案 revision/confirmation/authority/source 绑定、占位符、OOXML、排版、原子发布和交付清单。

## 统一入口（模型/WorkBuddy 必须遵守）

唯一文书工具是 `document.render-v1`；通过 `scripts.documents.runtime_cli render --workspace <工作区> --request <请求文件>` 提交模型的一次性完整正文。请求字段、八类文书结构和失败处理以 [统一文书工具](../document-render.md) 为准。

## 先判断文书目标

- 劳动关系仍存续、用户希望要求单位履行具体欠付工资或其他用工义务时，使用 `employment_obligation_demand_letter`。
- 用户已经完成被迫解除分析、计划依据劳动者法定事由解除劳动合同并准备通知时，使用 `forced_termination_notice`。
- 已经发送或已经生效的解除只做历史索赔分析时，不把仲裁材料改写成新的解除通知；只有用户明确提出新的计划解除动作，才重新说明风险并取得新的确认。
- 已发送但送达事实不明时，先核对通知内容、发送时间、收件地址或账号、签收/接收证据和生效主张；事实未清前只能继续分析或准备候选，不能取得或消费新的动作确认。
- “已发送”不等于“已送达”或“已生效”；历史索赔不产生第二封通知。只有寄件截图或本人陈述时，不把待核的生效日当作外发确定事实；继续工作、签收争议等反向材料按条件情景处理。新的解除动作仍须重新确认其独立范围。

催告函不得写入“逾期即解除”，不得替代被迫解除通知书，也不得作为生效裁判文书履行催告。被迫解除通知书不得由催告函自动转换；模型应根据当前事实和用户目标分别起草。

### 本次文书范围

起草前按[文书契约的起草前确认](../document-render.md#起草前确认)核对主路径确认，然后核对本次结算选择的来源：

1. 在用户原话中找到“通知书要求单位结算哪些款项”的明确答复，已有选择直接复用。案情分析纳入欠薪、讨论过补偿或请求草稿，都不回答这个问题。
2. 用户只确认“以欠薪为暂定理由，其他未核实事项不写”时，记录理由已确定、结算项目待选择；当前回复只问“结算部分仅请求欠薪，还是还纳入经济补偿？”并等待答复。尚无选择时保持未起草，也不写“用户明确选择仅欠薪”的主张记录。
3. 收到明确项目选择后，档案记录保留该选择的用户原话，在当前回复中沿用已获授权的候选目标开始起草和生成；已完成的摘要确认及草稿请求直接复用，不再问“是否按这个范围制作”。事实金额待核用占位，不要求用户再次同意占位；实施解除或外发的确认留在之后的专项边界。一般保留其他权利不变成具体请求。

仅有用户概述签字文本或零散片段时，风险提示保持条件表达，例如“若全文确含已结清或放弃权利条款，可能增加后续主张和举证风险，需结合完整文本核对”。查看完整文本及签署背景前，不把概述转成该文件已经导致某项权利消灭的确定结论；无需索取全文才能继续一般分析或保留候选稿。

## 起草与绑定

`sections` 必须按以下顺序提交完整、不为空的模型正文：

- 催告函：`收件人`、`劳动关系说明`、`具体义务`、`履行期限`、`沟通与保留权利`；
- 被迫解除通知书：`收件人`、`解除意思表示`、`解除理由`、`结算与手续`、`落款`。

正文使用对应文书的普通语言；candidate 保留必要的用户陈述来源、材料未核说明和待补占位，external_final 才须核实真实要素。内部待办列表、档案记录标识、工具字段、风险分、诊断和推理不进入正文。工具不会从正文猜测或补写主体、理由、金额、日期、送达方式或法律依据。

标题使用注册文书名，标题核对等提示放入独立核验清单。催告函的最后区块先写沟通及权利保留正文，再以换行单独列出签署人和日期；通知书使用独立落款区块。填写空间在对应签名或日期位置保留明确占位，签署区按多行、整体右缩进且块内左对齐排版；工具只处理明确分行的签署信息，不从同一段叙事中猜测或拆写落款。

### 欠薪解除候选稿的已知值

起草“解除理由”时，逐项从当前档案写入正文，保留用户陈述性质：

| 当前已知内容 | 正文中的处理 |
| --- | --- |
| 用户陈述的入职时间 | 保留已知年月或日期；只知道年月时具体日待核，不把整个时间换成占位 |
| 用户陈述的约定月薪 | 写出数值，并说明来自用户陈述、合同原文及工资构成待核；不是已核工资基数或欠薪合计 |
| 正常提供劳动及实际付款状态 | 沿用已述事实，付款状态与应发、已付、差额的未知数额分开 |
| 具体欠薪月份、金额等尚未提供 | 只为这些缺项保留待核或待补占位 |

render 前对照档案核对正文实际包含已知入职时间和月薪及其来源；聊天摘要、档案或核验清单不替代正文。材料仅由用户称持有时，只说明拟作为证明、内容及证明力待核。

锁定要素至少覆盖：

- 两类文书的标题、劳动者和用人单位主体、具体主张/义务、日期和落款；
- 金额按[通用锁定要素](../document-render.md#锁定要素与档案绑定)区分候选事实金额与计算结果：用户陈述月薪在相应事实区块引用 `F-*`，请求及结算金额仍引用 `CAL-*`；正文金额与绑定值一致；
- 被迫解除通知书的解除理由应同时绑定当前档案中的 `CL-*` 主张和 `E-*` 证据；`E-*` 若仅记录用户称持有材料，正文也只能写为拟提交、内容待核的线索，不能称这些材料已“佐证”或“印证”解除理由；不能用分析假设、冲突事实或未核对材料替代；
- 送达方式、解除生效日期等不同事实分别绑定，不把一个日期或一种动作语义复用于另一个字段。

candidate 缺少劳动者姓名、用人单位名称、最后工作日或签署日期的真实值时，在正文对应位置声明并使用 `【待补：...】`；落款可写“通知人：【待补：劳动者姓名】”，交付供人工核对。标题、已知解除理由及其主张和证据引用仍须与当前档案绑定；不得编造事实以通过校验。`external_final` 必须补齐真实主体、日期与签署绑定，且拒绝任何占位符。

## 被迫解除 external final 的窄门禁

candidate 不消费高风险确认，仍可帮助用户检查完整正文、事实、金额和送达计划。external final 只在以下条件同时满足时调用：

1. 档案中存在一条当前 revision 的完整高风险实质确认；
2. 确认的动作类别和范围确实覆盖本次被迫解除通知，用户作出明确选择并表示同意，而非拒绝或歧义；
3. 确认记录包含风险、替代方案、确认时间、绑定 revision 和 `source_refs` 来源引用；
4. 本类 external final 必须有当前适用且已核验的 `AUTH-*` 记录，以支撑当前解除规则；
5. 主体、理由、证据、日期、金额和正文通过统一文书确定性检查。

模型负责在确认前用普通语言说明解除主体、理由、日期、程序、送达不确定性、时效、基数、对方抗辩、后果和替代方案，并明确说明不会自动发送、提交、签署或上传。档案提交器只追加 confirmation 记录并绑定 revision；`document.render` 只校验记录，不维护确认卡、gate、流程状态或重试轮次。

动态现行规则核验失败时，一般分析、金额和 candidate 继续；只有实质依赖该规则的 external final 被阻断。候选不得冒充可外发定稿，工具 warning 由模型转成普通语言说明。

## 交付与恢复

统一工具返回真实 DOCX、独立“仅供核对，请勿外发”的核验清单、机器交付清单和校验摘要。核验清单不显示记录 ID、路径、JSON、哈希、模型推理或诊断；用户仍需在 Word/WPS 中检查字段、金额、分页和落款。

遇到 revision、绑定、confirmation、authority、OOXML 或发布冲突，先读取当前案情档案，按错误位置重建一次请求；不得在下游猜测模型正文或改写锁定值。任何失败都不得留下新的半成品；相同案件、revision、文书类型、模式和内容摘要重放只返回同一 canonical 结果。
