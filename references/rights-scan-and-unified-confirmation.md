# 权益扫描、最终补充与统一确认

本参考规定模型如何在主要案情采集完成后主动发现遗漏、收拢当前工作范围，并在分析、金额测算或文书准备前取得一次普通自然语言确认。它是模型的行为指导，不是新的运行时工具协议。

## 责任边界

模型决定何时停止追问、何时扫描、如何解释候选和缺口、何时开放最终补充、如何收口范围，以及如何用自然语言取得确认。模型读取案情档案并使用既有档案提交器的 `create`、`read`、`commit` 原子记录能力。

不把扫描或确认实现为固定问卷、状态机、确认卡、Presenter、全局门禁或重复工具协议；也不要把它们包装成固定的工具调用流程。不要新增权益扫描脚本、确认脚本或需要客户端选择的分析器。档案提交器只负责 Markdown 的原子写入、revision 冲突和恢复，不选择权益、不判断违法、不决定下一问题、不生成用户文案。

## 16 类权益目录

以下 16 类是模型主动提醒的常见候选目录，不是所有劳动争议请求的穷尽清单，也不是违法项目清单。目录外或复合事项保留用户原意，按争议路由（包括社保、公积金行政路径和复杂争议）分析，不强迫归入错误类别。

| 权益类别 | 面向用户的普通语言 | 可能涉及的方向（仅作提示） |
| --- | --- | --- |
| `wage_arrears` | 拖欠工资 | 工资未按约定或应付时间支付 |
| `unilateral_pay_cut` | 单方降薪工资差额 | 未经有效协商降低工资或待遇 |
| `sales_commission` | 销售提成 | 提成规则、业绩记录或结算争议 |
| `project_bonus` | 项目奖金 | 项目奖励约定、条件或发放记录 |
| `performance_bonus` | 绩效奖金 | 绩效规则、考核结果或奖金支付 |
| `annual_bonus_or_thirteenth_salary` | 年终奖金或十三薪 | 年终奖、十三薪约定和发放条件 |
| `workday_overtime` | 工作日延时加班工资 | 工作日超过正常工时的工作 |
| `rest_day_overtime` | 休息日加班工资 | 休息日工作及调休情况 |
| `statutory_holiday_overtime` | 法定休假日加班工资 | 法定节假日工作及工资记录 |
| `statutory_allowance` | 法定津贴补贴差额 | 法定津贴、补贴或特殊岗位待遇 |
| `unused_annual_leave` | 未休年休假工资 | 年休假应休、已休和折算支付 |
| `other_paid_leave` | 其他法定带薪假权利或工资待遇 | 病假、婚假、产假等法定带薪假相关事项 |
| `social_insurance` | 社会保险 | 缴纳、补缴情形及行政处理路径 |
| `housing_fund` | 住房公积金 | 缴存、补缴情形及行政处理路径 |
| `unsigned_contract_double_wage` | 未签书面劳动合同二倍工资 | 书面合同、签署时间和存续期间 |
| `termination_remedies` | 离职、辞退相关补偿 | 解除/终止主体、理由、程序和补偿 |

## 何时与如何扫描

当主要事实已经足以形成带条件的初步判断时，模型停止穷尽追问；在最终开放式补充前做一次完整扫描。模型先读当前案情档案，识别用户已经提出、档案已有当前处理记录或已在本轮明确处理的类别，再从 16 类目录中排除已经提出的类别。不得把同一类别再次作为“新发现”询问。

扫描应使用一个普通语言的多选式提醒，说明候选需要事实和证据核实，可以选择“可能相关”“暂不确定”或“目前没有其他事项”等自然语言。可以把多个类别放在同一个语义问题中，但仍只能有一个需要用户回答的问题。扫描结果只是候选，候选不等于违法或成立，也不认定可仲裁或一定能获得金额；模型同时解释需要补充的事实、证据缺口、可能的行政分流和更有利方向的适用前提。

扫描结果需要落入同一份 `案情档案.md`，通常作为 `claim` 记录保存类别、候选性质、当前依据和后续变化。记录所用的内部类别编号和状态只服务模型与档案，不向用户展示。不要创建 `rights-scan.json`、扫描回执、缺失清单或第二份事实源。

## 当前范围状态

权益记录可以使用下列内部状态表达当前工作范围；它们不是法律结论，也不是实体权利是否存在的判断：

- `mentioned`：用户已经提到，但还没有决定本轮是否处理；
- `potential`：扫描或开放补充发现的候选，尚未收口；
- `selected`：用户明确纳入当前分析；
- `pending`：用户明确暂缓，可能等待事实、证据或以后处理；
- `excluded`：用户明确表示当前不处理或不主张。

`selected`、`pending` 和 `excluded` 都可以被用户之后修改。`pending` 必须保留在档案中，不能在下一轮或确认时静默丢弃。`excluded` 只表示当前工作范围不处理；向用户明确说明“不处理不等于永久放弃实体权利”，除非用户另有明确、充分且适合当前高风险边界的选择。任何状态变化都由模型依据用户的新话和档案当前 revision 生成 `replace` 或 `append` 记录；档案提交器不自动推进状态。

暂缓及内部存档不会自动中断或中止仲裁时效；各请求的起算、中断/中止和程序需按案件事实分别核对。临近期限时先用普通语言提示及时核对实际可行的仲裁、向单位主张权利、有关部门救济等法定路径及证据，并说明记录或候选稿不等于已申请仲裁、不能承诺“保住时效”。真正要签署和解、结清或放弃权利时，另走重大权利处分的高风险说明与选择，不以范围状态替代。

纳入当前分析有用户目标和可描述的事实基础即可；证据薄弱可条件化分析并提示补证，不因缺工资条等单一材料自动排除。进入可外发文书前再逐项核对法律基础、可受理程序、事实/证据、金额和竞合；无事实基础或关键冲突的候选不得包装成确定请求。

权益收口不是新的确认卡或全局阶段。模型可以在一次普通回复中解释各候选所缺事实和范围影响，只问用户本轮哪些纳入、暂缓或当前不处理；此轮不同时询问最终补充或摘要确认。用户答“本次只处理工资、奖金和加班费”后，在回应这条答复时先记录范围选择，接着单独问最终补充；这次范围答复既不是最终补充，也不是摘要确认。有歧义时只澄清当前范围，不要求用户填写机器枚举。

## 最终开放式补充

范围选择明确后，回复用户时只开放一次宽泛的最终补充机会，例如询问是否还有未提到的重要事实、材料或特别希望处理的事项，并等待答复。用户已要求继续分析或准备候选稿时，记录范围后就提出这个尚缺的问题，不能只列待核项便结束，让用户再说“继续”才推进。用户说没有新事实时，记录补充已完成，在该次回复中展示当前完整摘要并只问是否准确。三个问题分别等待用户答复，已有步骤直接复用，无新事实不得循环。

如果答复带来事实或范围的实质变化，模型可以只针对受影响的类别或交付目标重新开放一个必要的补充/澄清问题；事实或范围实质变化才允许重开，不得重新扫描全部 16 类，也不得为了保持旧阶段名称而要求无意义的“继续”。新事实先按普通用户陈述落入档案，再由模型判断是否需要把相关候选从 `excluded` 或 `pending` 改回可讨论范围。

## 一次自然语言确认

在形成分析结论、确定金额或准备文书前，模型用一段用户能理解的普通语言展示并询问一次当前工作内容。至少覆盖：

1. 关键事实及哪些仍是用户陈述、证据支持事实或分析假设；
2. 当前权益范围，包括纳入、暂缓和当前不处理的项目；
3. 主要口径，例如期间、工资基数、适用规则或条件情景；
4. 重要假设、证据缺口和会改变判断的前提；
5. 拟交付内容，例如条件化分析、计算明细、证据计划或候选文书。

完整摘要确认须在最终补充之后单独提出，只问摘要是否准确。确认应允许用户用自己的话确认、修正或拒绝；只选择权益范围、只回答待核问题、没有纠正摘要或要求继续，都不能推定为确认。用户拒绝时，说明可以继续补充或暂缓；必要即时风险提示和一般条件说明可继续，候选起草仍等待当前摘要确认。用户回答含义不清时，明确指出尚不能判断其是否同意，并只提出一个自然语言澄清问题。工具确认卡、JSON、复选框或逐项机械签字都不能代替普通语言确认。

确认请求待答期间，如果用户补充或修正事实/范围，先更新档案并重建覆盖当前事实、待核项、范围、口径、假设和交付内容的完整摘要，再对最新摘要询问一次确认。“待核”“先按已知继续”等答复只记录待核项或继续事实收集，不表示确认。“我理解风险，先要通知书候选稿，不发送”明确了交付目标与不发送边界，但没有确认尚未展示的完整摘要；沿用已完成的范围与补充步骤，只补当前缺失的一步。即使用户已要求候选稿，也要等当前摘要获得明确确认后再开始分析、测算或准备文书；renderer 的 `confirmation_refs` 只绑定高风险最终化，不改变这项对话顺序。

自然语言确认记录必须通过既有档案 `commit` 原子写入，并绑定本次确认所依据的当前档案 revision。先 `read` 得到 revision `r`，再以 `expected_revision=r` 提交一次 `confirmation` 记录；成功后的新档案 revision 为 `r+1`。确认记录的 `content_markdown` 单独写一行 `绑定档案修订版本：<r+1>`，例如提交前为 5 时写 `绑定档案修订版本：6`；该字段名、冒号和纯数字值供文书交付入口读取，不能写成“本确认绑定档案修订版本 6”或只写“档案修订版本：6”。记录还应保留关键事实、权益范围、主要口径、重要假设、拟交付内容和用户自然语言确认摘要。工具只负责原子提交，不判断“确认”二字是否代表真实知情同意。

后续内部分析、计算、档案记录和文件渲染都使用同一份有效确认，不得新增工具级、文件级、发布级或案件包级重复确认；不得新增重复确认。高风险不可逆动作的实质知情确认属于后续专项边界，不被本次普通确认替代，也不在这里扩张高风险规则。

## 事实或范围变化后的失效

模型读取档案当前 revision，并将其与最近一次自然语言确认绑定的 revision 比较。事实、权益范围、主要口径、重要假设或拟交付内容发生实质变化时，旧确认只覆盖变化前内容，必须向用户说明已失效的影响，并只重新确认受影响范围；不要求整个案件回到起点。没有实质变化时，不重复确认。

重新确认仍是普通自然语言，不创建第二套 gate、ledger、轮次令牌或确认状态机。用户拒绝或再次含糊时，档案保持未确认/旧确认失效的可观察状态，模型不得继续声称已取得当前确认。

## 用户可见隔离

用户只看到自然语言的事实摘要、候选解释、一个当前问题、必要限制和下一步。不得向用户展示 `selected/pending/excluded` 等状态名、内部类别编号、`record_id`、`CONF-*`、JSON、revision、档案路径、CLI、工具协议、模型推理或诊断载荷。候选应称为“可能方向”“需要核实的事项”等，不称为违法清单、确定权利或保证结果。

对用户明确区分“本次暂缓不等于时效中断”和“本次不处理不等于永久放弃”，同时只提出一个当前需要回答的问题。时效紧急风险可先于完整收口提示，但不能跳过外发文书本身所需的确认与核验。
