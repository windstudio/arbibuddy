# 制品生命周期与仓库卫生

发布任务先读 [发布规范](release-workflow.md)。公开下载布局见 [Release 下载布局](release-downloads.md)：历史 Release 保留既有附件，后续新建完整 Release 采用安装包、源码与发布资料包、校验文件三个上传附件。

本规则约束开发仓库，不是面向终端用户的运行时 Skill 指令。

## 唯一去向

- `.scratch/` 只保存 Spec、Issue、研究笔记和小型诊断证据；不得放安装树、完整测试工作区或正式发布包。
- `--temp-root/<run-id>/`（源码树外）保存分层测试运行产物。每次运行使用独立子目录，结束后清理临时目录；仓库内 `tests/runs/` 仅保留兼容占位或小型诊断摘要。Agent Eval 失败调查期间可在同一临时根保留结构化轨迹、安装清单和 `failure-pack.json`，调查结束后仍须清理完整输出，只将小型结论写入 `.scratch/`。终态交付另保存清理前校验的 `delivery-evidence.json`；只有虚构 Scenario 的显式 `--retain-deliveries` 才允许在运行目录暂存可打开的交付副本。
- 项目正式根目录的 `dist/<VERSION>/` 保存当前 `VERSION` 的正式安装包、发布门禁记录、发布清单和可复验发布证据。独立 worktree 只能构建、验证和暂存；版本目录名必须与源码 `VERSION` 完全一致。
- 低层构建函数可以把制品写入受控临时目录；正式入口验证后才原子晋级到 `dist/<VERSION>/`。

## 禁止项与清理

- 不把 `dist/`、安装 ZIP/tap、完整测试输出、缓存、日志、私钥或信任登记提交到 Git。
- 发布失败不得留下可被误认为正式版的半成品；清理时先确认是否为权威来源重复项，不删除用户数据、唯一夹具或历史发布说明。
- 新的发布入口必须在写入前拒绝版本不一致、越界、`.scratch/`、`tests/` 及仓库根目录等目标。

## 验证证据

发布清单至少记录：版本、平台、客户端适配包名称、文件摘要和验证状态；同一版本目录中的包、清单、门禁记录和证据必须相互绑定。Git 卫生检查覆盖禁止路径、重复安装树、测试运行产物和敏感材料。
